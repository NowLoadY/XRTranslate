# 媒体播放时滚动和切页卡顿

## 原因与处理

Linux 的 MPV 视频线程与 wgpu 共用 EGL 上下文。离开媒体页后，原实现虽然跳过
画面绘制，但 MPV 的跳帧调用默认仍等待音频时钟，期间一直持有 UI 需要的图形锁。
追踪中可见每帧约 33 ms 的等待，连续争用使欢迎页滚动出现秒级停顿。

另外，界面每次布局和刷新都会同步查询播放器的进度、暂停状态、声道等属性，
可见画面也通过 `recv()` 等待视频线程，进一步耦合了界面响应与播放进度。

- 可见与隐藏的视频提交都关闭 MPV 内部的目标时间等待，并配置
  `video-timing-offset=0`，由播放器在应显示的时间通知新帧。
- 播放状态改为 MPV 属性事件维护的快照；界面读取快照，控制操作异步提交。
  重新加载文件时保留未变化的观察值，失败事件仍传递给现有错误显示。
  文件加载、音视频参数变化及播放重新就绪时，合并请求一次异步状态快照，
  补齐 libmpv 对部分嵌套声道属性遗漏的变化通知。
- Linux 视频提交最多保留一个未完成任务；界面复用现有纹理，完成后再刷新。
  调整大小时等提交完成再替换纹理；销毁时先退出并回收视频线程。
- 隐藏更新合并通知，避免队列堆积。音频滤镜只在文件加载或用户修改路由时设置，
  不在 `PLAYBACK_RESTART` 中反复设置，避免滤镜修改再次触发播放重启。

Windows 的隐藏跳帧路径同样关闭目标时间等待。离开媒体页仍继续播放。

## 验证

2026-10-29，在同一台 Ubuntu 开发机上，用隔离配置、Xvfb 软件图形环境及
同一个 1280×720、30 fps、120 秒 H.264 测试视频比较修改前后的 release 客户端。
每阶段经本地 UI Director 连续发送 60 次滚轮操作，间隔 10 ms。
下表测量请求进入界面处理的往返延迟，**不是屏幕或视频帧率**。

| 场景 | 修改前中位数 | 修改后中位数 | 修改前最长 | 修改后最长 |
| --- | ---: | ---: | ---: | ---: |
| 播放时滚动左侧导航栏 | 21.01 ms | 14.68 ms | 40.87 ms | 29.48 ms |
| 播放时滚动媒体页内容 | 20.89 ms | 15.33 ms | 33.36 ms | 28.62 ms |
| 后台播放时滚动欢迎页 | 290.08 ms | 7.71 ms | 2875.94 ms | 17.30 ms |

真实客户端检查覆盖暂停后进度稳定、暂停时拖动进度、继续播放、欢迎页后台播放、
反复切页、窗口缩放、播放结束后重播，以及暂停或播放时重新打开同一文件；
缩放后的帧截图确认视频仍正常显示。
测试产物在开发机的 `target/media-interaction-check/`，不包含用户配置或账号。

播放器回归测试使用真实 libmpv、临时 WAV 和空音频输出，不需要显示器或声卡：

```sh
cargo test --locked -p rust-client --features mpv --lib plugins::media --release
cargo test --locked -p rust-client --features mpv --lib plugins::media::backend::mpv::tests --release -- --ignored
```

这些测试验证重复打开、暂停状态、进度与时长更新、EOF 重播及异步加载失败。
最终 release 构建通过，38 项常规媒体测试及 2 项真实 libmpv 回归测试通过。
Windows 原生图形运行尚未在本次 Linux 环境验证。
